# 爬虫优化分阶段实施方案

## 总目标

- `basecrawler` 保持独立、无浏览器依赖，并逐步增强现代站点静态爬取能力。
- `browcrawler` 复用 `basecrawler` 的基础爬取、URL 规范化、scope、去重和队列能力，再增加浏览器运行时发现。
- 每阶段完成后必须运行针对性测试、与上一阶段或已保存基线对比，并记录各工具运行时间。
- 以经核验的有效页面/API 召回率、候选准确率、稳定性和完成率衡量效果，不以原始 URL 数量单独判断。

## 指标定义

- **有效 URL 召回率**：发现的经核验有效 URL 数 / 目标核验集中的有效 URL 总数。
- **候选准确率**：抽样核验为有效的 URL 数 / 抽样检查的候选 URL 数。
- **轮次稳定性**：同站多轮 URL 集合的 Jaccard 相似度。
- **运行时间**：从工具进程启动至退出的墙钟时间；报告同时保留每站、每轮、每工具的秒数和状态。
- **完整率**：在声明预算内完成的扫描数 / 已启动扫描数。超时和失败结果不得记作完整结果。

开始设定召回率和准确率门槛前，先建立经核验的目标 URL 集合。现有真实站点 URL 数只能作回归参考，未经访问验证的候选不算有效 URL。

## 阶段一：basecrawler 基础爬取可靠性

**目标**：稳定完成传统站点和现代站点的基础静态爬取，保留现有有效发现，并能解释扫描何时结束及预算是否耗尽。

**范围**：

- HTML 链接、表单 action、robots/sitemap、静态资源和已有 JS 静态提取。
- 区分发现预算与访问预算；记录来源、深度、访问状态、HTTP 状态及停止原因。
- 建立离线 fixture，覆盖普通 HTML、相对链接、重定向、sitemap、表单 action 和基础 JS。

**验收**：

- 离线 fixture 中所有可静态发现的确定 URL 均被发现，召回率 100%。
- 对当前已验证的传统站点回归集无有效 URL 丢失。
- 五个可用框架站点各运行三轮；完成的重复运行稳定性 Jaccard ≥ 0.90。
- `basecrawler` 运行不启动、不依赖浏览器进程或浏览器 SDK。

**阶段测试与对比**：离线单元/集成测试；对比阶段开始前保存的 testasp、testaspnet 及框架站点基线。按站点记录 `basecrawler` 每轮运行秒数、发现数、访问数、完成状态和停止原因。

**状态**：已完成（可靠性基线与时间记录）。

**实现记录**：basecrawler 的 `--report` JSON 增加 `elapsed_seconds`；对比脚本每次运行均传入独立报告路径，并在 `results.csv` 记录进程墙钟 `duration_seconds`。报告保留扫描是否完整及预算/停止原因。另修正比较脚本：basecrawler 结果需合并普通输出和 `discoveries.jsonl` 来源发现记录；`results.csv` 分列记录结果 URL、来源发现 URL 和去重后的站内候选 URL。

**测试与对比**：`go test ./...` 通过（507 tests / 19 packages）；`python -B tools/crawler_compare.py self-test` 通过。7 个站点各跑 3 轮，共 21/21 进程正常退出，站点轮次 Jaccard 均为 1.0。basecrawler 扫描报告中的 `limited` 表示深度或 URL 预算触顶，不代表进程失败。

**与其他工具的差异复核**：用修正后的 basecrawler URL 集与此前已保存的其他工具结果逐站比较；传统站点复用三轮记录，框架站点只采用成功完成的记录，超时结果不计。testasp 与 Katana/Gospider 各有 35 条重合、basecrawler 多 3 条；与 Browcrawler 有 23 条重合、basecrawler 独有 15 条、Browcrawler 独有 2 条。testaspnet 与 Katana 有 16 条重合、basecrawler 独有 4 条。Vue 与 Katana 的 81 条 basecrawler 候选全部重合，React 与 Katana 重合 91 条；SvelteKit 与 Katana 重合 317 条。Next.js 的 basecrawler 候选远多于其他工具，主要来自 Next Flight 静态数据，不能直接视为页面路由优势。crawlergo 的候选数也明显偏高且运行较慢；自动交互产生的额外候选仍需验证。URL 差集只是候选对比，不等于有效路由召回率或准确率。

## 阶段二：basecrawler 现代站点静态分析

**目标**：仅通过 HTTP 响应、HTML、JS bundle、构建清单和静态路由配置，尽可能发现现代站点的页面和 API。

**范围**：

- 扩展 hydration/JSON 数据、模块脚本、动态 chunk、JS AST、动态 import、fetch/XHR 和路由表提取。
- 增加 Next.js、Vue/Vite、Angular、SvelteKit 的独立静态适配器，保留通用解析回退路径。
- 区分确定路由、路由模板和推测候选；限制 chunk 深度、脚本总量、字节数和参数展开规模。
- 抑制 ViewState/随机 token、正则、HTML 片段、MIME 字符串等误解析噪声，并保留原始 URL 与来源。

**验收**：

- 为五个框架建立经核验的“静态可发现 URL/API 集合”。
- 对该集合的静态页面/API 目标召回率 ≥ 80%，候选抽样准确率 ≥ 70%。
- 结果可追溯到 HTML、脚本、构建清单或路由配置；动态运行时才能确认的项明确标为待验证。
- 每站三轮稳定性 Jaccard ≥ 0.90，运行在声明预算内完成或明确报告停止原因。

**阶段测试与对比**：各框架解析器 fixture 测试；五个框架真实站点三轮扫描；和阶段一结果逐 URL 对比新增、丢失、有效性及每工具运行时间。静态解析新增有效 URL 才计作召回提升。

**状态**：进行中；Next.js Flight 截断治理子任务已完成。

**已实施子任务**：Next.js Flight 候选上限从 400 调整为 800；达到上限时优先保留页面/路由，再填充 bundle 候选。新增回归测试覆盖“大量 bundle 出现在路由之前”的 payload。

**子任务测试与对比**：`go test ./parse -run NextFlight` 通过（5 tests）；basecrawler 全量测试通过（507 tests / 19 packages）。Next.js 同配置三轮扫描稳定性 Jaccard = 1.0；Flight 候选仍为 696，但实际发出从 400 提高到 696，截断从 296 降到 0。进程均时由 23.24 秒变为 23.10 秒；站内结果集合仍为 17 条，未观察到有效 URL 数增加，说明当前深度 1、最多 20 页的测试预算限制了可见覆盖。对比记录在 `artifacts/crawler-comparison/phase2-nextflight-20261117/` 和 `artifacts/crawler-comparison/phase2-nextflight-cap-20261117/`。

**页面预算对比**：对 Next.js 保持深度 1，将 `max_pages` 从 20 提高到 100，各跑 3 轮。20 页配置均时 23.65 秒、平均输出 17 条结果 URL、1,421 条去重站内候选；100 页配置均时 102.94 秒、平均输出 60 条结果 URL、候选仍为 1,421 条，两种配置 Jaccard 均为 1.0。100 页配置每轮确实发出 100 次请求并触及 URL 上限，扫描仍报告 depth boundary；运行时间约为 4.35 倍，访问结果 URL 增加 43 条。该对比说明页面预算限制了访问覆盖，但不证明 1,421 条候选都是有效页面，也不把预算变化算作解析器召回提升。记录见 `artifacts/crawler-comparison/phase2-nextflight-budget100-rerun-20261117/`，自定义目标配置见同名 `phase2-nextflight-budget100-20261117/targets.json`。

**测试工具修正**：自定义目标 JSON 将 `host_rate` 读作浮点数，basecrawler 的 `--rl` 只接受整数，首次启动三轮均失败。比较器现将该参数规范为整数，并在离线自测中覆盖该情况；修正后 100 页对比三轮均正常完成。

**下一子任务**：建立 Vue、React、Angular、Next.js、SvelteKit 的经核验静态页面/API 样本，抽样检查候选状态并区分页面路由、API、静态资源与构建产物；据此计算解析候选准确率和静态召回率。再按证据补具体解析缺口，不能把 bundle 数量或更高页面预算直接记作解析器覆盖提升。

## 阶段三：browcrawler 复用 basecrawler

**目标**：以单向依赖方式共享基础爬取能力，避免重复请求和重复解析。

**范围**：

- 依赖方向固定为 `browcrawler → basecrawler`，不得形成反向依赖。
- 通过稳定 Go API/共享记录结构传递 URL 候选、来源、引用页、深度、方法和访问状态。
- Browcrawler 将浏览器 DOM、运行时路由和网络请求候选汇入共享去重/队列；保留每条发现的来源。

**验收**：

- 集成后 `basecrawler` 独立运行结果不回退。
- 同一规范化 URL 不会因静态与浏览器来源重复导航；来源信息仍完整。
- 输出可以分别统计 basecrawler 发现、浏览器新增、实际访问页面和待验证候选。
- 模块依赖检查确认只有 browcrawler 引用 basecrawler。

**阶段测试与对比**：接口/去重单测、集成 fixture 和传统站点回归；逐 URL 对比 basecrawler 独立运行与 browcrawler 集成运行，记录两者各自耗时及合并后的总耗时。

**状态**：待实施。

## 阶段四：browcrawler 运行时覆盖和完成率

**目标**：在静态结果上补充浏览器实际渲染和交互产生的有效路由/API，并解决框架站点超时导致的结果不完整。

**范围**：

- 记录 DOM、运行时路由、XHR/fetch、点击、滚动和表单提交等来源。
- 为导航、JS 分析、交互和候选队列设置独立预算、进度、检查点与停止原因。
- 交互/表单提交作为可配置策略；输出提交方法及其发现结果。
- 对脚本正则、HTML 片段和无效 URL 候选做语法及上下文校验。

**验收**：

- Angular、Next.js、SvelteKit 与 Vue、React 一样能在预设预算内完成，或报告明确可复现的停止原因。
- 框架核验集上，集成扫描相对 basecrawler 独立运行的有效路由召回提升 ≥ 20%。
- 候选准确率不低于阶段二基线；每类候选均可追溯来源和访问状态。

**阶段测试与对比**：五个框架站点各三轮；报告 Browcrawler 相对 basecrawler 的有效新增、重复、误报、超时和每轮运行时间。表单测试单独列出，不与只读扫描混为一组。

**状态**：待实施。

## 阶段五：统一基线与发布回归

**目标**：建立可重复的项目级对比基线。

**范围**：

- 固定目标 URL、scope、预算、速率、交互策略、工具版本和运行环境。
- 分别报告传统站点、现代框架站点、静态扫描、浏览器增强扫描。
- 抽样核验新增/丢失 URL 的 HTTP 状态、内容类型和路由有效性。

**验收**：

- 每个站点、每个工具、每轮都有运行秒数、运行状态、发现量、访问量和错误/停止原因。
- 超时和失败不计为完整扫描；未核验候选不计入有效召回。
- 基线重复运行稳定性 Jaccard ≥ 0.90；已核验有效回归集无意外丢失。

**状态**：待实施。
